# Fronk 0.7.0: a llama.cpp head for 3-bit weights

0.3.0 ran one file with one head engine. 0.7.0 adds a second path for the same
model: ISTA-DASLab's GSQ-RCO weights, about a third smaller in the cluster's
memory, with llama.cpp as the head's dense engine. [GSQ.md](../GSQ.md) explains
the design; this page lists what changed and who has to update.

**This is a source version.** It is the code that ran on the head of the
author's test cluster (an M4 Pro head and four nodes) in mid-November 2026; what
the nodes ran is recorded [beside it](../evidence/node-sources-20261116.md). No managers were
built from it and it has not been through the
[release qualification](../RELEASE.md#qualification): the downloads on the
Releases page remain 0.3.0. Use it from a checkout; programs built from it
report 0.7.0.

## What is new

| Part | Change |
|---|---|
| Head engine | A second dense engine, llama.cpp 0.9.0 with one patch (`tools/engine/gsq/`), built by `make gsq-engine` and chosen with `--engine gsq` on an Apple Silicon head. It keeps the dense part, the router, the shared expert and MTP on the GPU and asks the cluster for the routed experts. `tools/fronk_engine.py` supervises it: API, request queue, memory guard, emergency chat save |
| Model | A second unit format, cut without requantizing from the GSQ-RCO IQ3_XXS file: 2.185 GB per unit, 43.70 GB for all 20, against 3.35 and 66.94 GB. The head takes the format from its model file and tells the nodes. Native units are untouched and both kinds can stay on a node's disk |
| Node backend | `gsq`, a CPU backend for those units on x86 (AVX2) and ARM (NEON), built on kernels vendored from ggml. A slice routed to by several tokens is read and decoded once for all of them |
| Expert caches | Optional, GSQ only, off by default: a machine can hold the most used experts whole and compute them alone, while the slices cover everything else. See [the two kinds of node](../GSQ.md#two-kinds-of-node) |
| Transport | One call now carries up to 32 tokens (it was 8), and two calls can be in flight, so a 64-token prompt batch is two half-batches per layer. Requests can travel as Q8_K, 3,112 bytes per token, when every node confirms it (opt-in). A call that comes back incomplete is asked again, alone, with growing deadlines for about 30 s, before the head gives up. Every node has its own request socket, so one node can be asked again without the others. Replies travel in datagrams of up to 60 kB, and the head can tell nodes that share one of its interfaces to send large replies in turn (`PACE`), because two arriving together overran its Ethernet adapter |
| Connection | Discovery and link setup retry where a node was only slow to answer: a just-rebuilt program on macOS, a USB Ethernet adapter, a machine busy loading the model. A node still held by a head that vanished frees itself within seconds |
| Installer | `--engine gsq` on a head, kept by the installed configuration. For this engine the manager verifies local files (both shards, by size and SHA-256) and does not download them. A unit file already on a node is recognized instead of being sent again |
| Stopping | A head that is stopped lets the engine finish its pass and the supervisor save the chat. If the cluster is gone, the engine finishes that pass by itself from the model file |
| Console | Can also listen on one private cable address (`--listen`), keeps the head's output on disk, and its controls answer while the head is busy |
| Tools | `fronk_bench.py`, `quick.py`, `measure.py` and `profile_run.py` time fixed workloads through the API; `dense_ceiling.py` times the engine alone; `gsq-multicheck.c` checks the multi-token kernels; `caffeinate-plus-linux.sh` keeps a Linux laptop node awake with the lid closed |

## What did not change

The ds4 head, the Q4 file, native units, the Metal, NEON and AVX2 backends and
the installer workflow of 0.3.0 are all still there, and a head without
`--engine gsq` behaves as before. One limit moved for everyone: the widest call
is 32 tokens instead of 8. The Metal backend still computes 8 at a time and
splits wider calls into consecutive chunks.

## Who has to update

Every machine, together: head and nodes are one program built from one source,
and this version changed the transport and the widest call. A GSQ head needs
nodes that have the `gsq` backend. A head that keeps the ds4 engine sends
nothing new when it connects, but a cluster that mixes 0.3.0 and 0.7.0 machines
has not been tested.

## What was checked

| Check | Result |
|---|---|
| Real cluster | The GSQ path served chats on the author's cluster with the units spread over four nodes, at a median of [25.8 tokens per second](../GSQ.md#measured-speed) on short replies. The head's start-up test compares a layer computed by the cluster with an oracle from the model file before it serves |
| Same code as the one that ran | Head and engine only; three of the four nodes ran earlier revisions built from their own copies, recorded as patches in [node sources](../evidence/node-sources-20261116.md). By SHA-256, the program tree is the one whose binary was in service on the head from 11 to 18 November 2026. `tools/engine/gsq/prepare.sh`, run from nothing, gives an engine source tree in which no file differs from the one in service |
| Every step of the CI workflow, from a fresh source export | Pass on an Intel iMac (x86_64, macOS): documentation links, Python tests, backend modules, `make engine`, `make DS4= test-core` (41 groups, among them `gsq` with 22 checks), `make DS4= test-plane-cluster`, the installer lifecycle |
| `make DS4= test-q8-wire` | Pass on the same machine, 10 checks |

Not checked for this version: `make gsq-engine` to the end from this checkout
(it builds only on Apple Silicon), a cluster started from this checkout (the measured cluster had older node
programs), a packaged install of a GSQ head, the ds4 head on real hardware after these
changes, and any head other than the M4 Pro. Treat those as open until someone
runs them.

## Limits

- The GSQ head runs on Apple Silicon only and accepts one exact file.
- GSQ units are computed on CPUs. There is no Metal backend for them and no
  RAM + SSD placement.
- Expert caches and Q8_K requests are opt-in and have seen less use than the
  default path.
- The numbers in [MEASUREMENTS.md](../MEASUREMENTS.md) and
  [TEST_CLUSTER.md](../TEST_CLUSTER.md) describe 0.3.0 with the Q4 file. For
  this path there is one figure, in [GSQ.md](../GSQ.md#measured-speed).
